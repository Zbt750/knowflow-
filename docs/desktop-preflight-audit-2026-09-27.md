# 安装包前全面审计（2026-09-27）

## 结论与范围

可以开始桌面化开发，但当前不建议直接打包发布。发现 9 项可复现的运行/交互问题，另确认测试目录隔离风险和若干发布缺口。自动化正常路径通过不等于异常路径、内容准确率或安装包可用性全部通过。

本轮只检查，不修改业务代码。保留工作区已有改动；使用新建、可销毁的测试数据库和独立上传/索引目录。没有向外部模型发送私人资料，没有重启用户的 8000 后端或 5173 前端。审计脚本、原始结果和截图保存在被忽略的 `storage/package-audit/`；不能把它们作为安装包资源。

## 已复现的问题与修复方向

### B01 · P1：快速切换会话，旧请求覆盖新会话正文

- 位置：`frontend/src/pages/ChatPage.vue`，`openSession`（约 301–309 行）。
- 复现：延迟 A 会话消息请求，切到 B 并显示 B，释放 A；侧栏仍选中 B，但正文变成 A。
- 影响：用户可能在看 A 内容时把后续问题发送给 B。
- 建议：请求序号/取消控制，并在写入消息前检查当前 session_id；加载状态也须遵循同一归属。

### B02 · P1：引用加问题超过 4000 字，失败后输入和引用丢失

- 位置：`ChatPage.vue` 的引用收集及 `send`；`backend/api/routes/chat.py` 的 AskRequest。
- 输入框限 4000 字，但引用拼接在限额之外；每条引用虽有限长，没有总预算。
- 浏览器实测：4000 字问题加短引用，最终请求 4019 字，返回 422；草稿长度变成 0，引用也消失。
- 建议：校验最终请求总长，显示剩余预算；确认请求接收后再清空，失败时保留或恢复草稿/引用。不得悄悄截断问题。

### B03 · P2：失效会话/消息请求错误导致整块问答进入错误边界

- 位置：`ChatPage.vue`，`openSession` 未捕获消息读取错误。
- 浏览器模拟普通 404“会话不存在”，点击历史记录后整个问答工作区消失，显示全局错误边界。
- 建议：在页面内处理删除竞争、网络故障与重试，保留侧栏、输入和之前可用正文；错误边界作为最终兜底。

### B04 · P1：DOCX 表格与段落顺序错乱，可能污染章节召回

- 位置：`backend/ingestion/document_parsers.py`，先读取所有 paragraphs，再读取所有 tables。
- 合成文件原序：第一章甲→甲说明→甲表格 111→第二章乙→乙说明→乙表格 222。
- 实际文本：第一章甲→甲说明→第二章乙→乙说明→甲表格 111→乙表格 222。
- 影响：表格可能落入错误标题范围，模型得到错误的章节归属；不是只影响排版。
- 建议：按文档块顺序解析，并测试表格所在标题、索引后的 chunk 范围。

### B05 · P1：上传限制只检查压缩文件大小，解压后内容无上限

- 位置：`backend/ingestion/source_io.py` 的 10 MiB 文件上限，以及 DOCX/PDF 解析流程。
- 有界测试：约 49 KB 的压缩 DOCX 被接受，解析出 11,000,219 字符。没有做危险的 GB 级压测，也没有宣称已测到崩溃。
- 风险：大量文本/chunk 引发内存、CPU、索引时间与页面阅读压力；PDF 同样缺少页数/提取文本上限。
- 建议：ZIP 展开大小/压缩比/条目数检查，页数、字符、chunk 数限制，以及可终止的解析隔离。线程超时不等于停止底层解析。

### B06 · P1：不可信 Origin 的 multipart 上传仍会入库

- 位置：`backend/app.py` 的 CORS 配置及资料上传接口。
- 隔离 API 实测：携带 `Origin: https://untrusted.example` 的 multipart POST 返回 201，数据库产生 1 条资料；响应无允许跨域读取头。
- CORS 限制读取响应，不等于阻止简单表单请求修改数据。本轮没有部署恶意网站，没有读取或泄漏用户密钥。
- 建议：桌面本地服务对所有修改接口做访问控制，而非仅保护设置接口；启动随机令牌、Origin/Host 校验、进程边界结合设计。

### B07 · P1：第二个后端启动会取消共享数据库中正在生成的回答

- 位置：`backend/app.py` 启动恢复逻辑，统一将 generating 消息改为 cancelled。
- 隔离复现：第一个应用中构造 generating 消息，启动第二个应用后，该消息被改为 cancelled。
- 建议：安装包单实例锁、进程所有权和 generation 租约/心跳；只恢复确定已失去所属进程的任务。不能把启动第二实例视作第一实例崩溃。

### B08 · P2：上传文件落盘后数据库失败，会留下孤儿文件

- 位置：`backend/services/material_service.py` 的文件保存与后续 flush/commit。
- 隔离注入保存文件后的 SQLAlchemyError 并回滚：数据库记录 0，新增源文件 1。
- 建议：事务失败补偿清理、异常路径测试和可安全运行的孤儿文件核对；文件系统异常也应转为用户可理解的错误。

### B09 · P2：全空格会话名称可以保存为空

- 位置：`backend/api/routes/chat.py`，min_length 在 strip 之前校验。
- POST title 为三个空格返回 201，保存 title 为空字符串；重命名校验存在同类问题。
- 前端通常会先 trim，所以这是接口边界缺陷，不代表正常 UI 每次都会触发。
- 建议：规范化后做长度校验，覆盖创建及重命名。

## B10 · P1：测试数据库隔离不等于文件/索引隔离

只配置 APP_ENV=test 和独立 TEST_DATABASE_URL 时，Settings 的 upload_dir/chroma_dir 仍可能与开发环境相同。只读配置探测确认两者均相同。

`scripts/prepare_e2e_data.py` 会对配置的向量库执行 clear，异常恢复还可能删除配置的索引目录。标准 `run-e2e.ps1` 显式指定测试目录，因此标准入口已有保护；手动运行辅助脚本时仅换数据库仍有清除开发索引的风险。

本轮没有执行这种危险清除，所有审计运行均使用专属目录。建议所有测试入口硬性检查解析后的上传/索引路径，采用独立测试默认目录，拒绝与开发/用户数据目录重合，不能仅以数据库名称判断安全。

## 常规 E2E 的 3 个失败需修正并重跑

1. `history.spec.ts`：读取 URL 中资料 id 时只等列表出现，没有等资料内容请求和 URL 同步完成，得到 null。证据指向等待时序不足；需修正等待后再完整验证前进/后退，不据此断言历史功能已经通过。
2. `navigation.spec.ts`：用精确名称“高等数学”匹配按钮；新可访问名包含“已选 N 个知识点”，导致旧选择器失效。应保留可访问信息并使用稳定定位。
3. `state-matrix.spec.ts`：移除最后一个知识点后点击已禁用的生成按钮，等待至超时。当前禁用行为符合防止空范围生成的设计；用例应断言 disabled 和请求数为 0。

上述是当前发布测试门禁失败，不能忽略。它们与 B01–B03 的新产品缺陷不是同一批问题。

## 安全与完善项

- Git 忽略配置涵盖真实 .env、storage、.pgdata；检查未发现这些路径被跟踪。不是全面历史秘密扫描。
- `.dockerignore` 缺少 .env/.env.* 和密钥文件排除。现有 Dockerfile 显式 COPY，未发现它把 .env 复制进最终镜像；仍存在构建上下文包含凭据的风险，不能写成“已泄漏”。安装包应使用资源白名单，排除真实数据库、上传、密钥、评测原始记录。
- 设置页已经可写、已有前端单测、隐藏 h1/页面标题/上传可访问名已接入；旧报告的这些判断不再成立。
- 问答的部分未配置模型/异常文案仍指导改 .env 并重启，与安装包用户使用设置页的流程不一致。
- 会话列表和消息历史接口整批返回，前端没有虚拟列表；大量历史的性能风险未做千级真实数据验证。资料分页和知识树批次展示已有实现，不能再报“没有分页”。
- 整份文件读取有 50 chunk/24000 字符预算；超长文档需范围澄清，尚无面向整本教材的分层摘要方案。不能把预算存在直接当成所有回答缺失的根因。
- 今日学习题干、答案详解仍为普通文本；题库扩充至 Markdown/LaTeX 时需要与聊天/讲解页面一致的安全数学渲染。
- 分享会话是同一服务 URL；桌面本地地址不等于跨机器分享，应明确功能或提供导出。
- 当前种子 11 个知识节点、5 个可练叶子、22 道题，是示例覆盖，不是完整考研知识/题库。

## 安装包发布前必须完成的工程门禁

1. **桌面壳与资源清单**：当前未发现 Electron/Tauri 安装工程、后端 exe 打包配置或安装器产物。PyInstaller/Nuitka/Rust 工具也未就绪。Web 构建成功不能替代安装验证。
2. **用户数据路径**：相对 .env/storage 路径与当前工作目录耦合。资源只读目录和 LocalAppData 用户目录必须分离，适配 Program Files、中文路径、普通用户权限及升级。PyInstaller 的运行时资源路径机制见[官方说明](https://pyinstaller.org/en/stable/runtime-information.html)。
3. **数据库与启动编排**：开发脚本依赖系统 PostgreSQL 18 固定安装路径及固定端口；必须确定嵌入 PG 或数据库适配路线，完成初始化、凭据、迁移、种子、索引检查和可理解的启动状态，不能带上真实 .pgdata。
4. **页面与 API 接入**：前端使用 history 路由和相对 /api，后端当前没有静态页面/SPA 回退。不能直接打开 file://index.html 当作安装版，需要安全本地服务或协议桥接、端口选择及深链接处理。
5. **进程生命周期**：单实例、端口冲突、父子进程退出、异常终止、重复启动和任务恢复须实测；B07 需先解决。
6. **模型资源**：本地模型缓存约 183.3 MiB，当前 torch 目录约 501.6 MiB；不是最终安装包大小。需要运行库/DLL/模型/字体/讲解资源/迁移资源清单和版本校验，清洁电脑验证。在线 LLM 不应宣传为完全离线问答。
7. **备份与升级**：数据库、原始资料、设置的备份恢复演练；索引可重建；DPAPI 密钥绑定 Windows 用户，跨用户/机器恢复需重新配置。升级迁移备份、失败回滚、卸载保留用户数据政策都须落实。
8. **发布安全**：依赖锁定（Python 当前范围版本并非完整锁定）、漏洞扫描、许可证/SBOM、签名和更新信任链。若选 Electron，按[官方安全清单](https://www.electronjs.org/docs/latest/tutorial/security)设置隔离、沙箱、CSP、导航限制和 IPC 校验，不通过关闭 webSecurity 解决跨域。
9. **安装验收矩阵**：无 Python/Node/PG 的清洁 Windows、普通权限、中文路径、断网、端口占用、磁盘满、重启、升级、卸载/恢复。当前没有安装器，因此这些还未验证。
