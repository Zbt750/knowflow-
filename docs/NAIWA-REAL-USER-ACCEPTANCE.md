# NAIWA 真实用户交互验收标准

自 2026-11-09 起，奶蛙用户功能的验收必须由真实用户旅程和可查看的浏览器证据支撑。该标准适用于所有后续 R49 及以后验收目录。

## 每条旅程的必备记录

每个场景都要记录唯一编号、目的、初始状态、用户实际输入原文、奶蛙实际回复原文、下一步用户操作和后续回复、最终业务结果、API 或数据库回读、截图路径和结论。确认、取消、追加、移除、恢复等动作需要走完操作链路。

用户输入必须通过当前项目界面实际发送。回复必须从页面实际显示或真实消息记录读取。不得编辑页面内容或用静态页面、Mock、单测结果代替真实交互。真实截图由 Playwright 控制当前项目浏览器直接保存；不得裁剪、合成、重绘或只截取测试提示。

每个 RXX 目录必须提供：

- SCREENSHOT-INDEX.md：截图、实际输入/回复、核验依据和结论的索引。
- REAL-USER-INTERACTION-REPORT.md：可逐项阅读的用户原话、奶蛙原话和实际操作结果。
- REAL-USER-SCENARIOS.json：便于校验的结构化证据索引。
- screenshots/：按功能分类保存截图；文件名包含测试编号与操作阶段。

失败或部分完成的旅程也必须保存失败界面截图、控制台错误、失败请求、服务端日志和 traceback（如果存在）。不能删掉失败证据。

## 证据类型

每条旅程须明确标注证据类型；类型不可互相替代：

- A：真实浏览器 + 真实后端 + 隔离数据库。
- B：真实浏览器 + Mock API。
- C：真实 API + 隔离数据库。
- D：单元测试。
- E：模拟算法测试。
- F：在线真实模型调用。

奶蛙核心用户旅程优先使用 A。个人 AI 生成、审核和重试若标记通过，必须有 F 类型证据，并记录真实 Provider 调用及保存回读。B、D、E 不能支持真实产品旅程 PASS。

## 截图与视口

截图需保留用户输入、奶蛙回复、方案/确认卡片、最终结果或失败提示。多轮流程对每个关键阶段分别截屏。核心响应式场景记录 1440、430、390、360 像素视口的实际截图和溢出检查；未测的视口不得声称通过。

统一路径形式：

storage/quality-audits/naiwa-rXX-final/screenshots/<功能>/<测试编号>-stepN-<阶段>.png

## 结论规则

只有真实界面、实际回复、业务动作和持久化回读互相对应时，才可把相应场景标为 PASS。未运行、环境阻塞、只通过 API/单测或缺少截图的场景分别标为 NOT_TESTED、BLOCKED 或 PARTIAL。全量测试数量不替代用户功能验收。

报告生成后必须运行：

python scripts/validate_naiwa_real_user_acceptance.py storage/quality-audits/naiwa-rXX-final

校验器负责检查截图文件、场景记录、类型标签和证据引用的一致性；它不能替代人工观察真实截图。
