# Phase 6 教程生成规范：以项目能力增量为主线

> 本文为先前反馈形成的历史版本。已完整合并并增加前端/API死规则；唯一当前规范为[tutorial-rules.md](tutorial-rules.md)。与旧文冲突时以新规范为准。

日期：2026-10-16。根据第一篇样章反馈修订。**本规范覆盖旧设计中“独立lab作为主线”“每篇固定模板/固定面试题”的安排。**

## 1. 先纠正交付对象

要交付的是同一个复现项目逐步长出来的过程，不是一组算法实验。

每章必须回答：“读者完成以后，自己的复现工程新增了哪项可操作能力？”只会运行RRF函数、最后列出原项目路径，不算完成项目混合检索。

原来的RRF样章保留为可选算法预习，公式、单路去重、跨路累加、名次、稳定排序和测试讲解可复用。它不是合格的项目混合检索主线。原Agent样章同样只是确认机制实验，不能替代真实工具、业务服务、数据库事务与用户页面联调。

## 1.1 硬性教学方式：黑马程序员项目实战视频的文字版

**教程必须参照黑马程序员《黑马点评》《苍穹外卖》等项目实战视频的带做方式，把“老师带着学生在一个项目里逐步完成真实功能”的过程转化成Markdown。**参照的是教学组织和节奏，不是复制课程台词、代码或内容，也不能声称与这些课程有官方关联。

不能只在标题里加“黑马式”，或者把源码说明改成口语。读者应当产生这样的实际体验：老师先带我看需求，推导实现方案，告诉我现在打开哪个项目文件、写什么、为什么，然后立即运行观察，遇到问题知道沿哪条链排查，最后看到功能真的接进项目。

### 必须呈现的视频带做节奏

1. **先看功能效果。**展示本章结束时用户能完成的操作、接口输出或页面状态；示意效果与实际运行证据明确区分。
2. **需求推导，不先甩代码。**围绕当前项目的具体问题，说明为什么已有能力不够、接下来增加什么；重要方案可用流程图作“白板推导”。
3. **明确现场操作。**直接说明“现在打开复现工程中的哪个文件”“在什么位置完成哪项职责”。学生不用猜目录、函数签名、依赖和接线位置。
4. **分段编码、及时解释。**先写可运行的最小项目能力，再根据实际需求逐步完善；每段解释职责、输入输出、上下游和关键取舍，不逐字符翻译。
5. **关键节点立即停下来验证。**明确提示“先不要继续，运行这条命令/调用这个接口”，给出预期结果和检查方法。不积累几百行未验证代码后才启动。
6. **观察问题再升级。**利用真实可复现的限制或边界，引出下一步实现。不得为制造戏剧效果虚构故障，也不需要每节刻意写一版错误代码。
7. **接线、联调、验收。**把新代码接进当前复现工程，沿真实Service、数据库、API和必要页面验证，不以孤立demo运行成功收尾。
8. **承接下一段项目开发。**说清已经增加的能力、尚未解决的问题，以及下一章为何依赖本章；20天是一条连续开发路线。

### 文字表达与完整代码如何兼顾

- 可以用“我们先看这个返回结果”“现在先停下来跑一次”等引导语，但必须伴随具体操作，不能只堆讲师口吻。
- 核心部分采用“方案→编码→运行→观察→完善”的多轮带做；简单配置、CRUD与样板给完整实现并简讲，不强行拉长。
- 逐段带做不等于只给零碎代码：必须提供关键阶段的完整可运行文件，最后提供本章完整工程检查点。学生不需要自行拼接缺失实现。
- 不要求每篇采用相同标题，不要求每篇固定附面试题；高价值模块完成后集中做设计取舍和连续追问。

**判定标准：读者是否真的像跟着项目实战视频一样，把同一个复现项目的一项能力做出来并验证了，而不是读懂一个知识点以后，还得自己想办法接回项目。**

## 2. 什么叫“写真实项目代码”

- 原产品D:\考研跑通项目作为只读教材，不为教学修改已验收代码或真实用户数据。
- 教学使用**一个持续演进的复现工程**，保持backend、frontend、tests等真实模块路径与相应公开契约。
- 不给每个知识点新建互不连接的lab。每日阶段包是同一工程的检查点，不是20个不同产品。
- 从空目录逐步加入完整代码；不把最终产品复制进去当作“从零实现”。
- 框架/适配/普通CRUD可以提供完整配套并简讲，但必须列出文件、依赖、版本、职责和验证方法，不依赖原产品隐藏导入或运行资产。
- 未教能力暂不接线，不返回假成功；完成章节后再接到真实入口。
- 所有写入只用独立教学库、资料目录和Chroma目录，不能接5433真实开发库。

“真实项目文件”不意味着在原产品上操作，也不意味着把所有历史兼容脚本逐行抄完。

## 3. 正式章节的验收契约

章节开头应简洁说清：

1. 进入本章前，复现工程已经有什么；对应哪个可运行检查点。
2. 本章要让哪个用户操作发生什么变化。
3. 哪些项目文件需要创建/完整更新，哪些属于前置完整配套。
4. 本章结束后运行哪个服务/API/页面验证，预期什么字段/状态。
5. 哪些能力尚未接入，不能误当作本章成果。

正文围绕业务障碍推进：先有需求，写入工程，运行观察，再因真实限制增加能力。不是每篇强套相同的14项/24项标题。

每一步必须给完整可运行代码；长文件可在关键步骤提供完整阶段版本与对照解释。不能只给diff、伪代码或“去看源码”让学生自行补齐。配套最终文件与正文必须一致。

每章结束必须包含**接线后的验收**，不是以“以后可以回项目看”收尾：

- 规则/算法的单元测试；
- 对应业务服务和API的集成测试；
- 有用户入口的功能回到页面验证；跨章功能在模块终章完成整条用户链；
- 记录实际输出、失败原因和未验证部分。

不把整个RAG/Agent塞在一个课时里。允许模块拆成连续章节，但每章仍在同一工程产生可运行增量，模块终章必须把所有前序接起来。

## 4. RRF样章应当如何成为项目课

正式模块主题：**让资料搜索真正使用三路混合检索，而不是分别学三个概念。**

### 核实过的当前源码入口

| 职责 | 真实路径/符号 |
|---|---|
| HTTP搜索入口 | backend/api/routes/materials.py：search_materials，POST /api/materials/search |
| 请求契约 | 当前路由使用SearchRequest→RetrievalRequest，不发明另一套请求 |
| 检索编排 | backend/services/retrieval_service.py：search_chunks |
| 正文BM25/标题树召回 | backend/retrieval/keyword.py：KeywordIndex.search / search_title_tree |
| 向量适配 | backend/retrieval/vector_store.py：ChromaVectorStore |
| Embedding | backend/retrieval/embedding.py |
| 融合 | backend/retrieval/fusion.py：reciprocal_rank_fusion / fuse_ranked_ids |
| 重排 | backend/retrieval/rerank.py |
| MMR | backend/services/retrieval_service.py：mmr_select_hits |
| 混合检索集成测试 | tests/retrieval/test_hybrid_search.py |
| Context/回答 | backend/chat/evidence.py、backend/chat/service.py；在对应后续章节接入 |

附件里的RetrievalService类、backend/retrieval/title_tree.py、vector.py是说明性示例，**当前代码不是这些结构**。文档标题构建在backend/ingestion/title_tree.py；检索侧标题召回在keyword.py。不能照示意新建不存在的业务架构。

### 连续实现顺序

1. 前置章节完成资料上传、解析、Chunk入库、可用索引。先从复现工程中看到真实Material/DocumentChunk，明确资料范围。
2. 在相同工程完成正文/标题候选查询，运行阶段测试，检查实际ID和命中范围。
3. 接入本地Embedding与Chroma，得到真实向量候选；模型未缓存则报告该环节阻塞，不能换成固定候选后宣称真实检索通过。
4. 三路都可追踪后，因原始分数量纲不同，自然引入RRF。在backend/retrieval/fusion.py写完整实现。
5. 在search_chunks中接线：过滤→三路候选→融合candidate_k→回表读取权威正文→可选重排/条件MMR→最终Top-K。
6. 运行服务，调用POST /api/materials/search，核对实际hit正文、所属资料、章节路径、名次/分数证据与范围过滤。
7. 在独立数据库和资料/索引上做混合检索集成测试；不能只用融合函数的合成列表测试替代。
8. 回到资料搜索页面验证实际返回与定位。后续问答模块再接Context、引用、LLM与SSE，并完成整个RAG问答验收。

本模块可以分几篇，但不能让学生每篇重新建一个lab。RRF公式的小手算只作插入讲解，不替代工程主线。

### 本模块真正完成的条件

- 三路候选来自相应真实组件，能追踪，不是全部硬编码列表。
- 范围、ready/active_version过滤和回表过滤正常。
- 单路重复不加分，跨路支持可累加，同分顺序稳定。
- candidate_k和最终top_k职责不同，不偷偷提前丢掉融合证据。
- API返回与页面显示可核对；引用/模型回答未接入时明确标注。
- Optional Rerank未启用时不声称真实CrossEncoder已运行；MMR遵守实际条件。
- 单元测试、隔离集成与用户入口各自报告，不混称同一种验收。

## 5. Agent按同一标准纠正

主线是用户提出学习目标后，工程中的真实服务如何读取学习状态与库存、形成可确认草案并安全执行。

模型/工具消息协议可以先用OfflineProvider验证，但读取的业务事实、草案校验、确认与持久化应逐步接回复现工程的真实服务，不长期停留在一个内存演示系统。

- learning_task_tools.py读取事实和校验；不能让模型自报来源、版本或库存。
- learning_task_service.py实现有界循环和生命周期；confirm_task用事务、计划签名、版本/资格复验与幂等。
- learning_task_context.py只压缩送模副本，保留必要事实，不篡改审计轨迹或确认快照。
- learning_assistant_service.py负责意图/上下文衔接，最终回到实际页面。
- 单独的RLock/内存计划可以是短实验，但不能冒充生产事务或完整Agent实现。
- 不动毕业算法；不把草案、计划、辅助正确、个人生成题当正式完成证据。

## 6. 教学深度不平均

| 深度 | 对象 | 教学动作 |
|---|---|---|
| A / ★★★★★ | RAG、Agent、Context、LLM/SSE、关键事务和证据边界 | 项目内逐步实现、完整阶段代码、细解释、测试/接线/调试、必要设计取舍 |
| B / ★★★–★★★★ | 普通业务接口、模型配套、框架适配、部署 | 完整代码、重点解释、运行验收，不逐个普通字段拉长 |
| C / ★–★★ | 大量Vue/CSS、生成类型、历史批次与重复样板 | 完整必要配套；理解连接点，不要求独立重写全部 |

面试追问集中在模块总结和关键技术取舍，不在每一篇CRUD/环境说明后机械加题。篇幅根据真实难点变化，不能以文档数量或测试数量代替功能完成。

## 7. 真实证据与费用边界

- 合成列表能验证融合公式；不能证明真实召回质量。
- FakeEmbedder/OfflineProvider能验证协议和边界；不能写成BGE/DeepSeek效果通过。
- 独立隔离PostgreSQL可验证事务；内存对象不行。
- 真实模型测试必须另行授权数据、请求数与金额；教程不会自动收费调用。
- 浏览器、API、函数和真实模型验收分别记录，历史通过不能冒充本轮通过。
- Docker/安装包未验证则明确标未验证，不为课程虚构部署完成。

## 8. 下一份样章的交付检查

交付前逐项检查：

- 是否在同一个复现工程，而不是新建独立实验？
- 本章新增能力是否能被用户从实际入口使用？
- 是否给出了所有必要文件与完整实现，而不是仅贴最终源码？
- 关键步骤是否当场运行，有可观察输出？
- 是否写清前置章节/依赖，不让读者自行猜接线？
- 规则测试之后是否有对应集成/API/页面验收？
- 是否使用真实名称、路径、请求契约，未把说明性示意当已有代码？
- 所有尚未实现/尚未实测的能力是否清楚标明？

**本次只修正规范，未完成替代版混合检索正文，也没有运行真实数据库、Embedding、浏览器或模型验收。**原样章测试结果仍只适用于原实验；不能迁移为新主线验收。
