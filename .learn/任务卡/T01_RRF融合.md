## 一、这次要造的东西是什么

你在做一个 RAG 检索系统。搜索时同时跑了三路召回：

- 正文向量检索（语义相近）
- 标题树 BM25（章节名命中后向下展开）
- 正文 BM25（专有名词、公式名、代码串的精确匹配）

三路各返回一个**有序的 id 列表**。现在要把三份列表合并成一份，并给出一个统一分数用来排序。

难点在于三路的分数**量纲完全不同**：余弦相似度是 0–1，BM25 是 0 到几十不封顶。直接加权求和需要每换一个 embedding 模型就重新标定权重。

**所以不用分数，只用名次。** 这就是 RRF（Reciprocal Rank Fusion）。

## 二、验收标准（这就是你的需求文档）

### 常量 `RRF_K = 60`

平滑常数。它的作用：让第 1 名和第 2 名的差距不要过分悬殊，同时保证"两路都进前 10"明显优于"只有一路拿了第 1"。

### 函数 1：`reciprocal_rank_fusion`

```
reciprocal_rank_fusion(
    ranked_lists: dict[str, list[UUID]],
    *,
    rrf_k: int = RRF_K,
) -> dict[UUID, float]
```

`ranked_lists` 的结构是 `{"vector": [id1, id2, ...], "keyword": [...]}`，每个 value **已经按相关性降序排好**，顺序本身就是全部信息。

必须满足：

1. 每个文档的分数 = 各路得分之和；在某一路里名次为 `r`（**从 1 开始**）时，该路贡献 `1 / (rrf_k + r)`。
2. `rrf_k <= 0` 时抛 `ValueError`。
3. **同一路内部**重复出现的 id，只按它最靠前的那个名次计一次分。
4. 不同路之间必须独立累加——同一篇文档同时被两路召回，要拿到两份分。
5. 返回的 dict 按分数**降序**排列；分数相同时按 id 的字符串形式升序，保证同样的输入永远得到同样的输出顺序。
6. 空输入返回空 dict，不报错。

### 函数 2：`fuse_ranked_ids`

```
fuse_ranked_ids(
    ranked_lists: dict[str, list[UUID]],
    *,
    top_k: int,
    rrf_k: int = RRF_K,
) -> list[tuple[UUID, float]]
```

复用函数 1，取前 `top_k` 条，返回 `(id, 分数)` 的列表。`top_k <= 0` 直接返回空列表。

### 函数 3：`rank_map`

```
rank_map(ids: list[UUID]) -> dict[UUID, int]
```

把名次列表转成 `{id: 名次}`，用于在最终结果里回溯"这篇是从第几名捞上来的"。名次**从 1 开始**。

## 四、四个最容易踩的坑（先看不许改代码）

1. **名次从 0 开始算。** `enumerate` 默认 0，公式要 1。`1/(60+0)` 和第 1 名的 `1/61` 差得很远，测试会用 `pytest.approx` 精确断言，一定挂。
2. **去重范围搞错。** 去重的 `seen` 集合必须**每路新建一个**。放到循环外面就变成全局去重——"两路都召回"的文档只能拿一份分，`test_rrf_agreement_beats_single_route_lead` 会挂。
3. **同分不稳定。** 只按 `-score` 排序的话，同分项的先后取决于 dict 插入顺序，`test_rrf_is_deterministic_on_ties` 有可能偶然通过、换个 Python 版本就挂。排序 key 要是 `(-score, str(id))`。
4. **`fuse_ranked_ids` 里又重新排了一遍序。** 融合函数已经排好了，这里只需要截断。重新排是多余动作，也可能引入浮点比较的细微差异。
